# Doc site to 0.9.0 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the documentation site from the 0.3.x feature set it currently describes up to what odysseus 0.9.0 actually does, starting with the pages that contradict the tool.

**Architecture:** Next.js App Router with Markdoc. Each page is `src/app/docs/<slug>/page.md` with YAML front-matter (`title:`) and a `{% .lead %}` first paragraph; the sidebar is a hand-maintained array in `src/lib/navigation.ts`. Renaming a page means moving a directory, updating that array, and fixing inbound links — Markdoc will not catch a broken `/docs/...` link, so the sweep is manual and is part of the work.

**Tech Stack:** Next.js, Markdoc (`{% callout %}` is the only custom tag in use), Tailwind. `npm run build` is the only check that exists — there are no tests.

**Source of truth:** the gem source at `/home/tsultrim/Code/WaConstellation/WaSystems/OdysseusProject/Odysseus` at version 0.9.0, and its `odysseus-cli/README.md`. Where a doc page and the code disagree, the code wins and the page changes.

**Repo:** `/home/tsultrim/Code/WaConstellation/WaSystems/OdysseusProject/Odysseus-doc-site`

## Global Constraints

- **The working tree has uncommitted changes** (`Gemfile`, `Gemfile.lock`, `src/app/docs/license/page.md`). Never run `git checkout`, `git stash`, `git reset` or `git clean`. `git add` only the files your task names.
- **Every factual claim must be checked against the gem source before it is written.** A page promising what the code does not do is the same defect as a README doing it. Cite the file you checked in your report.
- `accessories:` and `odysseus accessory` **still work** and print a deprecation notice. Pages must say the old spelling is accepted and deprecated — not pretend it never existed, and not present it as current.
- `odysseus setup` is **Ubuntu 24.04/26.04 only**, is for getting a single host going, and is not a provisioning tool: preparing servers at scale belongs to OpenTofu or equivalent. Every page that mentions it carries that framing.
- Deploys **never** gate on distro. Only `setup` does. Do not let the Ubuntu restriction leak into statements about deploying.
- `npm run build` must pass at the end of every task.
- Match the existing page voice: short lead sentence, `##` sections, fenced `shell`/`yaml` blocks, `{% callout %}` sparingly.

Extend the `### Remove` section. Verified against `odysseus-core/lib/odysseus/orchestrator/dependency_deploy.rb:95-121`:

- `remove` finds its containers **through the dependency's config block**, so deleting the block from deploy.yml first strands the container: `remove` then answers `Dependency 'redis' not found in config` and nothing else will find it either. Remove first, then edit.

- A container whose block is gone keeps running and does not appear in `dependency status`, which lists what the config declares rather than what the host runs (`dependency_manager.rb:44-56`).

### Task 3: New page — `odysseus setup`

**Files:**
- Create: `src/app/docs/cli-setup/page.md`
- Modify: `src/lib/navigation.ts`

**Interfaces:**
- Produces: `/docs/cli-setup`, linked from Tasks 4 and 5.

- [ ] **Step 1: Read the code first**

`odysseus-cli/lib/odysseus/cli/setup_commands.rb`, `odysseus-core/lib/odysseus/setup/{escalation,public_key,preparer,docker_apt}.rb`, `odysseus-core/lib/odysseus/host_paths.rb`, and `odysseus-cli/README.md`'s `### setup`. Everything below must match what you read; where this plan and the code disagree, the code wins and you say so in your report.

- [ ] **Step 2: Write the page**

Front-matter `title: setup`. Lead: prepares a fresh host so odysseus can deploy to it as a non-root user.

Cover, each verified:

- What it does: creates the user `ssh.user` names, adds it to `docker`, installs the resolved public key by **appending**, creates the state directory, installs Docker if absent, then opens a **second SSH connection as the new user** and proves Docker and the state directory work from there. Success is reported only if that passes.
- `--as USER` — the identity it connects *as*, default `ubuntu`. `--as root` needs no sudo. Passwordless sudo is required for any other identity, because odysseus runs non-interactively and cannot answer a password prompt. If the default is wrong the error names the flag.
- `--key PATH` — repeatable; overrides the key source. A `--key` that resolves to no valid public key refuses, naming the path, rather than falling back.
- `ssh.user: root` is **refused**: setup exists to enable non-root deploys, root needs no preparation, and deploying as root already works.
- Reads **no new config keys** — user from `ssh.user`, hosts from `servers.*.hosts`, keys from `ssh.keys`.
- Docker install: from Docker's official apt repository; keyring and sources file replaced whole every run; apt runs non-interactively with a 300-second dpkg-lock wait and names the holder on timeout; **no repair of an apt state setup did not create**; the GPG fingerprint is deliberately unpinned. Success is `docker info` answering *after* the install, not apt exiting zero.
- Reports `:changed` distinctly from `:ok`; a second run against a prepared host issues no apt command at all.
- Ubuntu 24.04/26.04 only, refused by name otherwise — unlike `doctor`, which only warns, because a deploy needs a working daemon and does not care which distro provides it.
- A `{% callout %}` making the positioning explicit: this is for getting one host going; servers at scale belong to OpenTofu, Terraform or equivalent, and setup opens no ports and touches no firewall, swap, `sshd_config` or unattended-upgrades.

- [ ] **Step 3: Nav, build, commit**

Add `{ title: 'setup', href: '/docs/cli-setup' }` to the CLI Reference group, first, before `deploy`.
